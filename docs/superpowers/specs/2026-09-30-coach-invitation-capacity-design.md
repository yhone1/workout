# 教练邀请轮换与学员名额设计

日期：2026-09-30  
状态：用户已确认；按本设计实施。
依赖：`docs/superpowers/specs/2026-09-28-coach-student-gym-platform-design.md`

## 1. 目标与范围

让教练用可重复查看、单次有效的邀请链接招收学员；未注册用户可由链接注册并自动绑定，已有账号可在健身房训练中粘贴链接绑定。成功绑定后，教练侧的邀请码自动轮换。总管理员可定义教练等级及统一学员上限，也可逐个设置教练的专属上限。

本设计只扩展邀请、教练关系及名额管理，不改变会员权限、训练计划、训练记录、身体数据、照片审核、居家训练或账号体系。没有邀请码的独立注册流程保持现状，待用户另行决定。

## 2. 已确认的产品规则

- 每个教练只有一个当前可分享的邀请码；一个邀请码最多成功绑定一个学员。链接可由教练反复查看/复制，但不得由学员查看教练的替代码。
- 邀请有效期沿用当前规则：默认 7 天，服务端允许 1–14 天；过期链接拒绝绑定，有可用名额时教练端可生成新的当前码。
- 邀请链接供未注册用户注册并绑定，也供已有账号在学员空间粘贴绑定。一个学员同时最多绑定一位有效教练。
- 新用户的账号创建、教练关系创建、旧码消费和后续换码必须处于一个数据库事务中；失败时不遗留半注册/半绑定状态。
- 每次绑定成功后立即消费旧码、使该教练其他待用旧码失效，并在仍有名额时生成下一枚当前码。达到上限时不发新码；释放名额后自动恢复当前码。
- 总管理员可动态增删/修改教练等级及各等级上限，并为单个教练设置专属上限。个人专属上限覆盖等级上限；未分级且无专属上限的教练视为未配置，不能新增绑定。
- 调低上限不自动解除现有教练关系；超过新上限时保留已有学员，直到活跃人数低于上限前拒绝新增绑定。
- 教练可结束自己名下的学员关系。关系结束释放名额，但不删除学员记录；已有训练历史仍归学员账号。
- 普通管理员不管理等级/名额；相关配置 API 仅总管理员角色可访问。
- 名额变更、等级指派和个人上限设置记录操作者与时间，便于追溯。

## 3. 邀请码安全与呈现

当前服务端只存邀请码 SHA-256 哈希，因而无法在教练刷新页面后还原新码。新码将同时保存：

1. SHA-256 哈希，用于学员提交时查找/校验；
2. 使用 AES-256-GCM 加密后的密文、nonce 和认证标签，用于仅向该教练本人重新展示当前链接。

加密密钥由服务端环境变量 `COACH_INVITE_ENCRYPTION_KEY` 提供，值为 base64 编码的 32 字节随机密钥；密钥不进入仓库、API 响应或日志。缺少/格式错误的密钥时，服务仍可启动，但不得创建或展示新的可恢复邀请；返回清晰的配置错误。密钥需在服务重启和备份恢复后保持一致。更换密钥前须先轮换活动邀请码；未配置密钥不得回退到明文保存。

当前邀请只返回给已认证且身份与 `coach_id` 匹配的教练。学生接受成功响应只返回关系结果，不包含教练替代码。邀请 token 仍放在 URL fragment（`#invite=...`）中，降低被访问日志及 Referer 记录的机会。消费、撤销或替换后立即清空旧码密文/nonce/认证标签，仅保留哈希与生命周期历史。日志不得打印 token、完整链接、密文或加密密钥。

升级前创建的邀请只有哈希、没有可解密密文：迁移保留这些记录和关系，不尝试恢复明文。未过期旧邀请在教练被分配名额后仍可用一次；教练工作台将标明旧链接不可重新复制，并可显式替换。一次旧链接成功绑定后，同教练其余待用旧码失效并改用可恢复的新码。

## 4. 数据与并发规则

- 新增教练等级表，保存稳定 ID、名称、非负整数上限和排序；总管理员可动态维护，上限 0 表示暂不招收学员。
- 新增教练名额配置，保存教练等级以及可空的个人非负整数上限覆盖值。有效上限为“个人覆盖值，否则等级上限”。缺失配置不默认为无限名额。
- 扩展邀请记录以保存加密 nonce、密文、认证标签及密钥版本，并用 `is_current` 标识教练当前可分享码；数据库约束确保每位教练至多一条当前码。旧记录这些字段为空且非当前，仍可读取。保留现有 `token_hash`、一次性消费与失效历史。
- 新增名额配置审计记录，保存操作者、目标教练、旧值/新值和时间；不保存邀请码明文。
- 接受邀请、检查学员已有关系、检查教练有效上限、创建关系、消费旧邀请、使其他待用邀请失效及生成替代码均在事务内完成。
- 接受和结束关系/管理名额变更都按教练账号行加锁，再计算活跃学员数。并发接受不能使人数超过上限。
- 当上限降低至低于现有活跃人数时不改写关系；只拒绝后续绑定。邀请码过期、撤销、已使用或密钥不可用时均拒绝接受，不提供越权回退。

## 5. API 与界面变化

- 教练工作台的“学员与邀请”显示活跃人数、有效上限、剩余名额和当前邀请链接；可复制当前链接，查看历史状态并撤销/替换当前码。首次打开且已配置名额、有空位时，按需生成首枚当前码；刷新后返回相同当前码。
- 教练结束关系成功后，若仍有空位则自动生成/恢复一个当前邀请码；若无空位则不发码。
- 新用户通过邀请注册时，注册请求附带 invite token，由服务端一次性完成注册与绑定；独立注册（没有 token）保持现状。
- 已注册学员在健身房学员空间粘贴完整邀请链接；前端仅接受本站链接并提取 token，也兼容已有版本的裸 token。服务端仍重新执行全部授权与上限校验。
- 管理工作台新增独立“教练名额”菜单：维护等级名称/上限、搜索并给教练指派等级、设置个人覆盖上限、显示活跃/上限人数及变更历史。删除仍被教练使用的等级时拒绝，要求先改派。
- API 错误应区分邀请无效/过期/已使用、已有有效教练、教练资格失效、名额已满、名额未配置和加密密钥未配置。UI 用简洁中文提示；不暴露其他教练或学员信息。

## 6. 迁移兼容与保护

- 新增可重复执行的数据库迁移；不重置数据库，不改用户、角色、教练关系、训练计划、训练会话、身体记录、照片或旧 `workout_records`。
- 不删除或批量撤销升级前的邀请码。旧邀请消费时执行与新码相同的资格、关系和容量校验，并在成功后过渡到加密可恢复的新码。
- 所有现有 `localStorage` 键、`thinMuscleAuthToken`、`/api/auth/register`（无邀请场景）和居家训练功能保持兼容。
- 新配置初始化为空；在总管理员配置首个等级或个人上限前，教练不能新增学员，但已有关系与数据保持可读可用。迁移不会凭空设定一个未获用户确认的统一上限。

## 7. 验收

1. 新用户通过有效邀请注册后自动绑定；对无效/过期/已使用/名额满的邀请码，事务回滚，不创建账号或关系。
2. 已注册用户粘贴完整本站链接可绑定；异站链接被拒绝；同一个 token 第二次接受失败。
3. 绑定后教练刷新仍能看到替代码；旧码失效；学生响应、数据库普通查询结果和服务日志中没有明文替代码。
4. 未分级教练不能新增绑定；个人覆盖值优先于等级；修改等级上限后新绑定行为正确。
5. 并发接受在上限边界下最多创建规定数量关系；调低上限不拆关系；结束关系释放名额并恢复发码。
6. 普通管理员和教练访问总管理员名额 API 均被拒绝；教练不能读取/修改他人名额或邀请码。
7. 升级前旧邀请与既有关系保留；旧邀请通过后自动过渡到可刷新查看的新码。
8. 现有会员、动作库、计划/逐组训练、照片审核、权限隔离和居家训练记录回归测试不受影响。运行态仍只使用 `http://localhost:3001`，没有得到用户明确请求前不启动、重建或重启服务。

## 8. 非目标

- 不决定或改变无邀请码时的开放注册政策。
- 不做学员申请教练、教练间转移学员、自动升级教练等级、支付、AI 审核或邀请码使用次数统计仪表盘。
- 不强制踢出现有学员以满足调低后的名额，不覆盖任何训练/身体/照片数据。
