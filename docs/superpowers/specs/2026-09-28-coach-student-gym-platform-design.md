# 教练—学员健身房训练平台设计

日期：2026-09-28  
状态：教练—学员平台原设计已进入实施；2026-09-29 统一入口与会员计划扩展经用户确认，待书面设计复核，尚未实施。`yhone` 为总管理员并默认拥有全部权限。

## 1. 目标与边界

在现有轻健身网站中增加多人健身房训练能力。教练为学员选分化、定个人计划、代记每组训练，学员登录后查看自己的计划与记录。第一版同时提供身体数据记录、照片审核和展示圈。现有居家推/拉/腿核心、MRT、Cindy 及其 `localStorage`/账号同步逻辑保持兼容，不以新系统替换。

本次扩展统一居家训练与健身房平台的登录入口和权限判断，并为后续会员计划留出能力。游客不能进入训练内容；居家训练和会员自助计划需要有效会员授权。教练邀请关系授权的教练计划不要求购买会员。现有居家训练功能、记录和存储键必须保留。

第一版在现有本机 Docker 环境开发、验收；架构不绑定本机 IP，后续可部署云服务器。云端部署是另一个任务。第一版不做 AI 审核、评论、教练自动选分化、学员自行填写训练组数据或照片体脂强制填写。

## 2. 角色与权限

| 角色 | 权限 |
| --- | --- |
| 管理员 | 授予/撤销教练资格，管理全站动作库，审核所有照片（包括私密照片），处理展示圈内容。`yhone` 为首个总管理员；不把所有普通注册用户自动设为管理员。 |
| 教练 | 创建邀请、管理自己名下的学员、从动作库选动作制定计划、逐组代记训练、查看该学员授权的身体数据与照片。不能修改全站动作库，也不能查看其他教练的学员。 |
| 学员 | 凭邀请注册/关联教练，查看自己的计划和训练记录；自己填写身体数据、上传/撤回照片及选择可见范围；不能改教练计划和训练组记录。 |

一个学员同一时间只有一位有效教练。支持多位教练，但教练资格需管理员授予，不能自行注册成为教练。邀请使用一次性或可失效的随机码，不凭可猜测的用户名建立教练关系。角色与学员归属在服务端逐次校验，隐藏页面按钮不算权限控制。教练关系变化时，旧教练失去后续访问权限；历史记录保留于学员账号，不转存到教练个人记录。

角色与会员资格是独立维度：`admin`、`coach`、`student` 控制工作台和管理操作；会员授权控制居家训练与会员计划。`yhone` 是总管理员，服务端策略为其授予全部权限，不要求会员记录。教练—学员有效关系允许学员查看教练已发布的计划及相关训练，不要求会员资格；此关系不自动授予居家训练权限。居家训练与会员自助计划必须有有效会员授权，未登录或授权缺失/过期时均由服务端拒绝访问。

支付接入前由总管理员手动授予、续期或撤销会员资格，记录生效日期和到期日期。到期日按 Asia/Shanghai 时区的当日结束计算；过期后阻止新的会员训练访问，不删除既有训练记录。会员历史和账号数据保持原有隔离规则。

## 3. 入口与主要流程

同一网站、同一账号和登录态。根路径 `/` 作为统一登录/训练中心：未登录显示登录与注册；登录后只显示该账号有权访问的模块。原居家训练保留为独立受保护模块（目标路径 `/home/`），健身房教练、学员和管理工作台继续由 `/gym/` 承载。直接访问受保护模块时，未登录用户先登录并返回原目标；已登录但缺少权限时显示原因和可用入口。居家训练与 `/gym/` 共用现有 `thinMuscleAuthToken` 登录态，不新增第二套账号或登录令牌。

训练中心按有效授权展示“居家训练”“教练/学员训练”“会员计划”“展示圈”和管理入口。居家训练入口只对有会员权限的账号及总管理员开放；教练计划按有效教练关系授权；会员自助计划按会员授权开放。管理工作台内的“照片审核”“动作库管理”和“会员授权”是分开的菜单与工作流。教练不能修改全站动作库或授予会员权限。手机和电脑端均可完成对应角色的主流程。

1. 管理员赋予教练资格；教练创建邀请；学员接受邀请并注册/登录，关联唯一有效教练。
2. 教练从三种分化模板选择一套，再按学员调整动作、顺序、组数、目标次数、目标 RIR、可选目标重量、预计时间。计划发布后学员可看下一次训练。
3. 学员到馆后，教练打开下一训练日，按实际组记录重量、次数、RIR及可选备注；可跳过或替换动作，草稿自动保存，结束时形成正式训练记录和实际时长。
4. 学员和教练都可新增体重、腰围、可选体脂记录。初始记录由任一方填写后，必须由学员核对确认；确认后初始记录不可修改。后续数值以新记录追加，历史不覆盖。
5. 学员上传照片并选择可见范围；管理员审核通过后按范围显示。公开照片可进入展示圈，登录用户可浏览和点赞。
6. 会员进入会员计划后，可自行配置计划，或选择 AI 推荐；AI 先生成可编辑草稿，会员确认后才加入自己的计划。

## 4. 动作库与训练计划

首批由开发方直接从 `D:\projects\ExerciseGymGifsDB-main` 选取并添加约 80–120 个常见健身房动作，不要求用户逐项筛选，也不批量无核对导入。开发方自行核对 GIF 内容、中文动作名、肌群和器械；只有素材含义、动作归类或演示正确性确实无法判断时才请用户确认。每个动作有稳定 ID、中文名、主要/次要肌群、器械、动作模式、推/拉/腿归类、动作要点、GIF 路径和适用分化。一个动作可被多个分化模板复用；筛选支持肌群、器械、推/拉/腿、模板归属及名称搜索。动作名称与 GIF 一一核对，避免错图。

内置推拉腿、上下肢、五分化模板。五分化默认胸、背、腿、肩、手臂；核心主要放手臂日末尾，腿日主项后可少量补充。教练决定学员采用哪种分化，系统不按性别、体重自动指定。训练日按计划顺序推进，不绑定固定星期；建议训练日可显示，但缺席不自动跳过。

会员自助计划与教练发放计划分开管理。具备有效会员授权的用户可以从动作库和分化模板自行配置个人计划，也可以提供训练目标、每周可训练时间、器材、经验和动作限制，让 AI 从已审核的动作与分化模板中推荐。AI 只生成带推荐理由的可编辑草稿；须用户确认后才能启用，不能直接覆盖教练计划、现行计划或历史训练快照。手动配置与 AI 推荐生成的计划都使用相同的版本化计划和训练记录结构。第一阶段不接支付或自动续费，会员授权由管理员手动维护。

模板是起点，学员最终使用的是教练发布的独立计划版本。改计划只影响尚未开始的训练；已完成训练存当时动作和目标的快照。已开始的草稿不会因计划修改而悄悄换动作。目标重量可以参考同动作上次实际重量，但不自动强制增加。进阶建议基于实际重量、次数、RIR和历史表现给教练，由教练确认后才修改未来目标。

## 5. 训练记录

每个计划动作有目标组数、次数范围/目标、RIR 和可选重量。教练在每组填写实际重量、次数和 RIR，默认带入计划目标或合理的上次值，所有值可改；备注可选。可记录动作跳过/替换及原因。休息计时仅辅助，不设强制结束时间；实际训练时长由开始、结束时间计算。草稿自动保存，意外刷新可恢复；放弃草稿不得删除此前已完成训练或身体记录。正式结束后保留计划快照与逐组实际数据，后续更正要留痕，不静默覆盖历史。

学员界面重点显示“下一次训练”和历史详情，不提供组记录编辑。训练进步曲线基于实际记录；训练建议只供教练决策，不在学员端自动改计划。

## 6. 身体数据、照片与展示圈

身体记录含体重、腰围、可选体脂及记录时间/录入人。初始记录在学员确认前为待确认状态，确认后锁定；后续变化通过追加记录形成趋势。体脂是用户测量值，不从 BMI 推算。照片与体脂均非必填。

照片由学员本人上传，选择“仅自己”“自己和教练”“公开”。无论可见范围，首次上传均由管理员审核；待审/拒绝内容不对其他普通用户展示。公开仅指本站已登录用户，不允许匿名访客访问。由非公开改为公开需重新审核，审核期间不得提前公开。照片文件保存在非公开存储中，经鉴权接口读取，不用静态目录直链。学员可随时撤回，撤回后立即从所有浏览入口消失；保留必要的审核操作记录，不以可访问的原图作为公开历史。管理员可下架违规内容。

展示圈第一版按时间浏览已审核且仍公开的照片，支持点赞，不做评论。展示昵称，不默认公开真实姓名、教练关系、体重、腰围或体脂；身体数据只有学员主动选择时才随照片展示。私密照片不会被展示圈索引或搜索到。未来 AI 辅助审核可接入，但不能绕过当前管理员审核规则。

## 7. 技术边界与数据模型

沿用现有 Node/Express、Postgres、静态前端和账号登录。新增模块独立于现有 `index.html` 的居家训练状态机，避免把新逻辑塞进既有大文件。原有 `workout_records(user_id,key,value)` 及所有现存 `localStorage` 键原样保留；新增健身房业务使用结构化关系表，例如角色、教练学员关系/邀请、动作、模板、计划版本、训练草稿/正式会话、逐组记录、身体记录、照片/审核、点赞。数据库变更采用可重复执行的迁移，并对现有数据做备份与兼容检查，不重新初始化用户数据。开始任何数据库迁移前，先核对位于项目外的 `yhone` 账号专属训练状态备份。

统一认证沿用现有账号及 `thinMuscleAuthToken`；不得因新增训练中心而创建平行账号或改动旧登录态。增加独立于 `user_roles` 的会员授权记录，至少包含用户、授权状态、生效日、到期日、授予人及创建/撤销审计信息。所有居家训练和会员计划相关的服务端读取与写入都核验有效授权；教练计划继续校验教练—学员关系和计划所有权。前端按权限展示入口只改善体验，不能替代 API 授权。总管理员 `yhone` 通过服务端明确的超级管理员规则获得全权限。

新增 API 按“身份 → 关系 → 资源”鉴权；学员 ID 不足以授权访问，必须核验当前教练关系或资源所有权。照片上传限制类型、大小并校验内容，存储路径不由用户输入决定。开发时可使用本机持久卷保存照片，并隔离出存储接口，以便将来迁移到云对象存储。互联网开放前需另行完成 HTTPS、强密码/种子密码更换、登录限流、备份与安全检查；本机开发验收不等于已可直接公网开放。

## 8. 开发顺序与验收

开发分五段，但第一版交付范围包含全部五段：

1. 账号角色、教练邀请、学员归属和后端权限。
2. 动作库、搜索、三种模板、学员计划与版本。
3. 教练逐组记录、草稿恢复、进阶建议、身体数据及初始确认。
4. 照片上传/审核/撤回/可见范围、展示圈与点赞。
5. 手机和电脑端联测、权限越权检查、旧居家训练回归。

验收至少覆盖：多教练互不可见；学员仅见自己数据；邀请关联与教练资格审批；三种分化计划定制与版本快照；草稿刷新恢复、放弃不影响旧记录；每组重量/次数/RIR 保存和教练确认进阶；学员确认后初始身体值无法修改；未审/私密照片不能在展示圈或直链获取；撤回立即停止展示；点赞状态正确；原有推/拉/腿核心、A/B、MRT/Cindy、音效和账号同步不回归。测试须使用专门测试账号与数据，不覆盖用户现有训练记录。优先复用现有 `http://localhost:3001` 服务；未经用户明确要求，不启动、重建或重启容器。

统一入口与会员计划属于原五阶段平台交付之后的扩展，书面设计复核通过后单独编制实施计划。建议顺序为：统一训练中心与登录回跳 → 会员授权及日期管理/服务端门禁 → 会员手动定制计划 → AI 可编辑推荐草稿 → 桌面、手机及旧居家训练回归。AI 服务提供方与密钥管理须在实施前另行确定；当前设计不假定或保存任何密钥。

统一入口与会员权限另需验收：游客打开 `/` 时只能看到登录/注册，直接访问居家训练或会员计划 API 均被拒绝；有效会员在生效日可访问，过期后新访问被拒绝且历史记录不丢失；`yhone` 无会员记录仍能访问全部模块；未购买会员的学员可通过有效教练关系访问教练计划，但不能因此进入居家训练；教练关系失效后不能继续读取该学员计划；会员手动授权、续期和撤销有日期且审计可查；AI 推荐只能保存为草稿，确认后才成为当前计划。

## 9. 非目标与后续

原教练—学员平台第一期不包含云端正式部署、原生 App、社交评论、AI 审核、支付、教练之间共享学员、学员自行更改教练发放的计划、以 BMI 自动定训练强度。照片展示圈的内容排序第一版仅按时间；算法推荐另议。

会员支付、自动续费和退款暂不接入；当前以管理员手动授予带生效/到期日期的会员授权。会员自助计划的 AI 推荐界面与草稿流程属于会员计划扩展，不得越权使用未经审核的动作或自动替换已启用计划。
